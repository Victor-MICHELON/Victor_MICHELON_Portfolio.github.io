Predicting Parkinson’s disease motor scores from noisy clinical data

Predict, for every patient visit, the motor score a patient would have without active medication, from noisy and often missing measurements. I ran it as a controlled lab: one locked evaluation protocol, one file per hypothesis, every run logged. The submitted blend of five models brings the cross-validated error from 16.51 to 2.51, on synthetic data.

  • −85%prediction error with our model, against a constant mean prediction (RMSE 16.51 → 2.51, cross-validated by patient)

The problem

In Parkinson’s disease, the MDS-UPDRS motor score depends heavily on levodopa. The OFF score, measured without active medication, says the most about the disease itself, but it is rarely measured, often noisy, and it depends on the rater and on the time since the last dose.

The task: for each visit, predict the true OFF score (the debiased target) from the observed ON and OFF measurements, the levodopa dose, the time since intake and the patient’s history.

  • Metric: RMSE at the visit level.
  • Hold-out: by patient, so no patient appears in both train and test.

The data

The data is synthetic: 44,590 visits from 5,576 patients for training, 11,013 visits from 1,395 patients for testing. Most columns have holes, and the most useful ones are missing the most often.

Note

The test set contains every visit of each test patient. Previous and next visits, per-patient averages and sequence models are therefore legitimate inputs: they never touch the target.

Approach

The repository is a Bob + skore project that goes from idea to submission. Bob drives the whole chain, with one evaluation protocol so that every run is comparable, and submits the best one.

Rules that kept the results honest

  1. Paired decision rule. Each run is compared fold by fold with a reference run. A gain with |Δ| smaller than std(Δ) is noise; a gain below about 0.02 RMSE is logged but does not justify a more complex submitted model.
  2. No leakage. Anything learned from the target (drug response curves, rater bias, encodings, stacking, scalers) is fitted inside fit_predict, on the training folds only, and splits are never made at the visit level.
  3. No tuning on the leaderboard. The public leaderboard was only used to check that it moved with cross-validation.
  4. A critic before costly runs. A leak-reviewer agent reads each expensive hypothesis before it runs.

Implementation

  • Locked protocol

    lab/cv.py scores every run with the same 5 GroupKFold folds by patient, stored in lab/folds.csv, and reports the out-of-fold RMSE.

  • One hypothesis, one file

    Each experiment is a file lab/experiments/eNNN_*.py exposing fit_predict, DESCRIPTION and FEATURES.

  • Automatic log

    results.csv and LOG.md record every run with its reference, its paired delta and a verdict: gain, noise or worse.

  • Agents and skills

    Bob agents (analyst, experimenter, leak-reviewer) and skills (/cv, /idea, /review, /submit…) with guardrails.

What worked

  1. Modelling the generating process rather than piling up features: the drug’s pharmacodynamic curve, an amplitude per patient, a scale per rater.
  2. A latent trajectory per patient, hierarchical then cubic, estimated by MAP with a skew-normal noise per measurement source. It gives the boosting model an excellent prior.
  3. Using the sequence of visits: lags, leads and sequence networks (BiGRU, Transformer) over each patient’s visits.
  4. Blending decorrelated models (boosting on the trajectory, sequence networks, a GRU on raw inputs) with non-negative least squares on out-of-fold predictions.

Limits

Limits

The data is synthetic, built for teaching. The scores are out-of-fold cross-validation, grouped by patient; I do not claim a leaderboard rank here.

What did not help

Several directions were explored and dropped for lack of a gain above noise: fine per-rater bias, per-patient stacking, pseudo-labeling, heavy network tuning, an MLP alone, an “amortized” Transformer alone. The findings are documented in lab/eda/ and lab/IDEAS.md.

Reproduce

python3 -m venv .venv && .venv/bin/pip install -r requirements.txt -r lab/requirements.txt

# quick test on one fold (not logged)
.venv/bin/python lab/cv.py lab/experiments/e002_hgb_basic_context.py --folds 0

# full run: 5 folds + test predictions, logged in results.csv / LOG.md
.venv/bin/python lab/cv.py lab/experiments/e022b_cubic_traj_quad.py --test --ref e002_hgb_basic_context

# out-of-fold NNLS blend
.venv/bin/python lab/blend.py e023_seq_nn e022b_cubic_traj_quad e025_seq_offset e026_seq_amortized --name b003_seq4

# submission: EstimatorReport on Skore Hub + submissions/<key>.csv
.venv/bin/python lab/submit.py b006_seq4_gruref --key b006_seq4_gruref

LightGBM needs brew install libomp on macOS (otherwise HistGradientBoostingRegressor is used); the networks use PyTorch. The Kaggle data goes in data/, read-only.

Python, scikit-learn and LightGBM gradient boosting, PyTorch (BiGRU, Transformer), pandas, skore, Bob
